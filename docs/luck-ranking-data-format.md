# 欧非排行榜 JSON 数据格式

排行榜使用一个轻量索引和按卡池拆分的详情文件。页面首次只读取总榜与卡池索引，用户选择卡池时才加载对应详情；浏览器不会重新计算或调整名次。

## 文件要求

- 索引：`public/data/luck-ranking.json`
- 卡池详情：`public/data/luck-ranking-pools/{poolId}.json`
- 编码：UTF-8（无 BOM）
- HTTP Content-Type：`application/json; charset=utf-8`
- 不能包含注释、尾随逗号、`NaN` 或 `Infinity`
- 每个欧榜或非榜最多 30 条，也允许为 0～29 条
- 数组顺序就是最终名次，前端不会再次排序
- 玩家 ID 必须在计算服务器写文件前脱敏为 `12***67`；JSON 中禁止出现原始 7 位 ID
- 建议先写临时文件，校验成功后原子替换正式文件，避免页面读到不完整 JSON

卡池 ID 同时用于拼接详情文件名，只允许字母、数字、下划线和连字符。索引不重复保存详情文件名。

## 索引文件示例

```json
{
  "dataType": "gacha-party-luck-ranking-index",
  "schemaVersion": 2,
  "generatedAt": "2026-08-26T12:30:00.000Z",
  "isSample": false,
  "total": {
    "label": "全卡池总榜",
    "range": ["2025-05-07T00:00:00+08:00", "2026-08-26T20:30:00+08:00"],
    "sampleSize": 28641,
    "lucky": [
      ["12***67", 1040, 17.33],
      ["23***45", 760, 18.1]
    ],
    "unlucky": [["34***89", 590, 59]]
  },
  "pools": [["140-1", "海风拂暑-复刻1", "/images/cardpools/140.webp"]]
}
```

`pools` 的每项固定为 `[poolId, poolName, imageUrl]`。上例对应的详情地址由页面直接拼成 `/data/luck-ranking-pools/140-1.json`。

## 卡池详情文件示例

`public/data/luck-ranking-pools/140-1.json`：

```json
{
  "range": ["2026-08-25T00:00:00+08:00", "2026-08-26T20:30:00+08:00"],
  "sampleSize": 1840,
  "spCards": ["1814", "1815"],
  "lucky": [
    ["12***67", 26, 6.5, [1, 3]],
    ["23***45", 31, 10.33, [0, 3]]
  ],
  "unlucky": [["34***89", 178, 59.33, [2, 1]]]
}
```

详情文件不再保存卡池 ID、名称、图片或文件名。`spCards` 顺序是 `["1814", "1815"]`，因此数量列表 `[1, 3]` 表示抽到 ID `1814` 1 个、ID `1815` 3 个。角色名称和 Q 版图片由网站根据 ID 从 `cards.json` 查找。

## 顶层字段

| 字段            | 类型    | 必填 | 说明                                                     |
| --------------- | ------- | ---- | -------------------------------------------------------- |
| `dataType`      | string  | 是   | 固定为 `gacha-party-luck-ranking-index`。                |
| `schemaVersion` | integer | 是   | 当前固定为 `2`。                                         |
| `generatedAt`   | string  | 是   | 数据完成计算的 ISO 8601 时间，必须带时区或使用 `Z`。     |
| `isSample`      | boolean | 否   | `true` 时页面显示“演示数据”；生产数据写 `false` 或省略。 |
| `total`         | object  | 是   | 全服总榜。                                               |
| `pools`         | array   | 是   | 卡池索引数组，可以为空；每项为 `[ID, 名称, 图片路径]`。  |

页面把最近一次成功读取的索引和读取时间保存在浏览器本地。进入页面时优先校验并使用本地数据；距离上次成功读取不足 30 分钟时不发起索引请求。卡池详情按需加载，并用索引的 `generatedAt` 作为缓存版本；索引更新后旧详情缓存自动失效。

## 榜单公共字段

| 字段         | 类型               | 必填 | 说明                                                        |
| ------------ | ------------------ | ---- | ----------------------------------------------------------- |
| `range`      | `[string, string]` | 是   | 统计起止时间，依次为开始、结束，建议使用带时区的 ISO 8601。 |
| `sampleSize` | integer            | 是   | 进入该范围的去重玩家数，必须大于或等于 0。                  |
| `lucky`      | array              | 是   | 最欧榜，建议按平均抽数升序，0～30 条。                      |
| `unlucky`    | array              | 是   | 最非榜，建议按平均抽数降序，0～30 条。                      |

总榜还需要 `label`，用于显示“全服总榜”等名称。

卡池详情还需要：

| 字段       | 类型     | 必填 | 说明                                                                          |
| ---------- | -------- | ---- | ----------------------------------------------------------------------------- |
| `targetRarity` | string | 否 | 省略时为 `SP`；常驻扭蛋写 `SSR`。 |
| `spCards`  | string[] | SP 卡池必填 | 此统计范围内合规的 SP ID，至少 1 个，不允许重复；顺序定义玩家数量列表的含义。SSR 卡池省略。 |

索引不必包含所有站内卡池。页面会列出站内全部卡池，未出现在索引中的卡池显示“暂无数据”；索引中出现站内尚未收录的新卡池时，页面也会根据索引中的名称和图片追加显示。

如果一个卡池的最欧榜和最非榜都没有符合发布规则的玩家，生成器不得把该卡池写入索引，也不保留对应详情文件；页面统一显示“暂无”。

## 玩家数组

为了减少体积，玩家记录不用对象。

### 总榜

```text
[playerId, pulls, averagePulls]
```

| 下标 | 类型    | 说明                                       |
| ---- | ------- | ------------------------------------------ |
| `0`  | string  | 脱敏玩家 ID，必须严格符合 `12***67` 格式。 |
| `1`  | integer | 统计范围内有效抽数，必须大于或等于 0。     |
| `2`  | number  | 所有 SP 实际花费抽数的算术平均值，由计算服务器给出。 |

### 卡池榜

```text
[playerId, pulls, averagePulls, spCounts]
```

前三项与总榜相同。第 4 项 `spCounts` 是非负整数数组，长度必须与该卡池的 `spCards` 完全相同；每个下标的数量对应同下标的 SP ID。数量为 0 也不能省略，否则后续位置会错位。

常驻扭蛋详情写 `"targetRarity":"SSR"`，玩家记录与总榜一样只使用三项数组 `[playerId, pulls, averagePulls]`，不保存或显示抽到的 SSR 角色及数量。

例如：

```json
{
  "spCards": ["1814", "1815", "2105"],
  "lucky": [["12***67", 52, 14.25, [1, 0, 3]]]
}
```

表示该玩家在这个卡池内共 52 抽，4 个 SP 的实际花费抽数平均为 14.25，其中 `1814 ×1`、`1815 ×0`、`2105 ×3`。页面只展示数量大于 0 的头像。

`averagePulls` **不能**使用 `pulls / SP 数量` 计算。限定、联动及各自复刻池内部存在保底继承，应使用以下口径：

1. 对同一玩家，把属于同一保底组的所有卡池记录合并，并按 `created_at`、记录 ID 升序排列。
2. 从上一个 SP 后开始累计抽数；遇到 SP 时，把当前累计值记为该 SP 的实际花费并将计数清零。
3. 单卡池排行榜先按完整保底组计算每个 SP 的花费，再按该 SP 实际出货时的卡池 ID 筛选；因此第一个 SP 的花费可能包含玩家在同组其他卡池中的垫抽。
4. 单卡池 `averagePulls` 是该池全部 SP 花费值的算术平均；总榜则是各保底组分别计算后，所有 SP 花费值的算术平均。

所以 `pulls` 只表示选定统计范围内的抽数，通常不会等于 `averagePulls × SP 数量`。

## 排序与发布校验

1. 最欧榜按 `averagePulls ASC`、最非榜按 `averagePulls DESC` 在计算服务器排好。
2. 平均值相同时，可用 SP 总数降序、抽数降序、玩家 ID 升序等稳定规则处理并列。
3. 每个数组最多 30 条；没有符合条件的玩家时写 `[]`，不能写 `null`。
4. 检查玩家 ID 严格匹配正则 `^\d{2}\*{3}\d{2}$`，原始 ID 不得写入或发送给网站。
5. 检查每条卡池记录的 `spCounts.length === spCards.length`。
6. 总榜候选人的统计范围总抽数必须严格大于 1500；1500 抽不入榜。全卡池总榜只合并普通 SP 卡池，高级常驻池和常驻扭蛋因概率不同必须排除。
7. SP 卡池候选人必须在该卡池抽到至少 5 个 SP；常驻扭蛋候选人必须在该池抽数至少 300 且抽到至少 15 个 SSR。所有单卡池最欧榜仍要求对应稀有度的平均抽数严格小于 36。SP 卡池最非榜要求平均抽数严格大于 37；常驻扭蛋 SSR 最非榜要求平均抽数严格大于 13。边界值 36、37 和 13 均不入对应榜单。
8. CDN 缓存 TTL 建议不超过 30 分钟，或发布后主动清缓存。
9. 发布时先原子写入全部卡池详情，再原子替换索引；索引发布后才清理不再引用的旧详情文件。

运行 `npm run ranking:sample` 可读取现有 `card_pools_full.json` 和 `cards.json`，生成仅包含脱敏 ID 的演示文件。它仅用于页面预览，不能作为生产排行。

## 体积说明

生产文件和仓库中的演示文件都可以直接输出压缩 JSON（不带缩进）。本文档保留格式化示例便于阅读；拆分后首次请求只包含总榜和卡池的 ID、名称、图片路径，单卡池玩家数据仅在用户选择该卡池时传输。
